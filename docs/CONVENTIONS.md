# تقفيلة — معايير المشروع

> آخر تحديث: 2026-06-26

هذه الوثيقة هي المرجع العملي للمطورين. إذا تعارضت مع وثيقة تاريخية، اتبع هذه الوثيقة والكود الحالي.

## نطاق المنتج

تقفيلة تطبيق تشغيل يومي، وليس نظام محاسبة أو ERP أو POS.

المعادلة الأساسية:

```text
الداخل - الخارج = الناتج
```

يدعم التطبيق:

- ملخص المبيعات اليومية حسب قنوات البيع.
- الخارج كعمليات مستقلة: مشتريات، مصروف، سحب.
- التقفيلات اليومية.
- السجل والتقارير والتصدير.
- المرفقات.
- تعدد المحلات داخل منظمة واحدة.
- أدوار المالك والموظف، مع وجود manager معماريًا.

## مصطلحات ممنوعة كتصميم منتج

| ممنوع | البديل |
|---|---|
| accounting / ledger / journal | entries / closeouts / cash movement |
| debit / credit | لا يستخدم |
| P&L | تقارير تشغيلية |
| tenantId كهوية منتج | organizationId |
| حذف مالي فعلي | void / restore |

## نموذج SaaS

المنظمة هي الجذر:

```text
Organization
  ├─ Stores
  ├─ Members
  ├─ Subscriptions
  ├─ Entries
  └─ Attachments
```

المعرفات المعتمدة:

- `organizationId`
- `storeId`
- `userId`
- `salesChannelId`

لا تضف `tenantId` بجانب `organizationId`.

## مصدر الحقيقة

في الإنتاج:

- DB/API هو مصدر الحقيقة.
- الجلسة الموقعة هي مصدر الهوية.
- لا fallback محلي لبيانات الأعمال.
- لا قراءة أو كتابة دائمة لعمليات أو تقفيلات أو محلات أو موظفين من المتصفح.

راجع `DATA_SOURCE_UNIFICATION.md`.

## بنية الكود

```text
src/
  app/                 routes only
  components/taqfeelah-app/
  core/
  domain/
  features/
```

قواعد:

- `page.tsx` يستورد feature أو shell فقط.
- الحسابات المرجعية لا توضع داخل React components.
- المنطق المشترك يوضع في `core` أو `domain` أو `features` حسب الملكية.
- لا تضف مسارات تشغيل بديلة أو بيانات محلية وهمية للتطبيق.
- `/app` هو مسار التطبيق التشغيلي.

## العمليات

أنواع العمليات:

```ts
type EntryType = "summary" | "purchases" | "expense" | "withdrawal";
```

قواعد:

- `summary` للداخل فقط.
- الخارج يسجل كعمليات مستقلة.
- الحذف المالي يكون `void`.
- الاسترجاع يكون `restore`.
- لا تستخدم حذفًا فعليًا للعمليات المؤثرة على الأرقام.

## التقفيلات

`DailyCloseout` يمثل تقفيلة يومية لمحل واحد. التقفيلة تشمل الداخل حسب قنوات البيع والخارج والمرفقات وسجل التدقيق.

السياسة الحالية:

- لا توجد مراجعة مالك للتقفيلات قبل الاعتماد.
- إرسال الموظف يعتمد فورًا في DB كـ `approved`.
- واجهة المستخدم تعرض الحالة كمرسلة/مراجعة حسب النصوص الحالية.
- تعديل المالك أو المدير لتقفيلة مرسلة يتم عبر `ownerEdit`.
- النسخة السابقة تصبح `voided` ولا تحذف فعليًا.

## المصادقة

في الإنتاج:

- دخول حقيقي فقط.
- جلسات موقعة.
- لا role picker.
- لا PIN أو OTP ثابت داخل الكود.
- لا أسرار داخل Git.

## `/app`

`/app` هو مسار التطبيق التشغيلي الوحيد. لا يوجد مسار تشغيل بديل للتطبيق.

واجهة `components/taqfeelah-app` هي تركيب الواجهة الحالي. أي تعديل بصري واسع يحتاج قرار واضح لأن الواجهة معتمدة كخط أساس.

## SaaS Admin

`/saas-admin` لوحة إدارة المنصة، وهي منفصلة عن تطبيق العميل. يسمح لها أن تكون desktop-first لأنها أداة تشغيل داخلية وليست تجربة العميل اليومية.

## قواعد الدمج

قبل اعتبار أي تغيير جاهزًا:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

ولأي تغيير يمس بيانات الإنتاج:

- أضف أو حدث اختبارًا مناسبًا.
- حدث الوثيقة المعتمدة المرتبطة.
- لا تعتمد على fallback لإخفاء خطأ API أو DB.

## تعريف "منجز"

الميزة منجزة عندما تكون:

- مربوطة بمصدر بيانات صحيح.
- محمية بالصلاحيات.
- لا تستخدم fallback مضلل في الإنتاج.
- قابلة للاختبار.
- موثقة في الوثيقة المعتمدة.
